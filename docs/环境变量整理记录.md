## 🎯 方案 A：Docker 优先统一配置

### 核心思想

**所有配置统一在根目录 `.env` 管理，Docker Compose 负责传递给各个容器。**

### 优势

1. **配置集中管理** - 只需维护一个配置文件
2. **避免配置冲突** - 不会出现多个配置文件不一致的问题
3. **简化部署流程** - 生产环境和开发环境使用相同的配置方式
4. **团队协作友好** - 新成员只需配置一个文件即可启动项目
5. **符合 Docker 最佳实践** - 通过环境变量注入配置

### 工作流程

```
.env (根目录)
    ↓
docker-compose.yml (读取并传递)
    ↓
├── backend 容器 (通过 environment 字段接收)
├── frontend 容器 (通过 environment 字段接收)
├── postgres 容器
├── redis 容器
└── minio 容器
```

### 本地开发支持

虽然推荐使用 Docker 环境，但仍然保留了本地开发的支持：

- `backend/.env.example` - 后端本地开发配置模板
- `frontend/.env.example` - 前端本地开发配置模板

这些文件主要用于：
- 不使用 Docker 的本地开发
- 配置参考和文档
- IDE 的环境变量提示

## 📝 使用指南

### 新项目初始化

```bash
# 1. 克隆项目
git clone <repository-url>
cd yueying

# 2. 初始化配置
make init

# 3. 编辑配置文件
vim .env

# 4. 启动服务
make up

# 5. 初始化数据库
make migrate
```

### 现有项目迁移

如果你已经有旧的配置文件：

```bash
# 1. 备份现有配置
cp .env .env.backup

# 2. 检查新的配置模板
cat .env.example

# 3. 合并配置（手动）
# 将旧配置中的值复制到新的 .env.example 格式中

# 4. 验证配置
make ps
make logs
```

## 🔒 安全建议

1. **永远不要提交 `.env` 文件到 Git**
   - 已在 `.gitignore` 中配置
   - 定期检查 `git status` 确保未被追踪

2. **定期更换密钥**
   - 生产环境每 3-6 个月更换一次
   - 开发环境可以使用固定密钥

3. **使用强密码**
   - 至少 16 位
   - 包含大小写字母、数字、特殊字符
   - 使用密钥生成工具

4. **备份配置文件**
   ```bash
   # 加密备份
   tar czf env-backup.tar.gz .env
   gpg -c env-backup.tar.gz
   ```

5. **限制文件权限**
   ```bash
   chmod 600 .env
   ```
